# Info

原理: 在运行时**加载**一个动态库文件(`.so`或者`.dll`), 随后**调用**里面的函数.

## 加载

1. 编译期加载
  我们非常熟悉了, 就是使用`-Llib -lraylib`链接在当前目录下`lib`文件夹中的`libraylib.so`动态库文件.

2. 运行时加载
  1. Linux `dlopen()`
  2. Windows `LoadLibrary()`

## 调用

> 问题在于面对一个未知的库文件, 我们该如何调用里面的函数.

我们需要一个查询符号或者变量的指针地址的函数, 但是尽管这样, 我们也没办法预测里面有什么函数, 然后做出操作, 所以本质上插件是一种**约定**.

调用函数的办法:
1. Linux `dlsym()` 
2. Windows `GetProcAddress()` 

# 方法讨论

## 导出函数指针

通过直接导出函数指针的方式来控制函数的使用. 缺点就是没有作用域等等方式的隔绝, 十分难处理, 限制非常大

## 导出插件结构体接口

导出一个结构体, 里面包含插件的基本信息, 例如版本号, 插件名称, 函数指针列表等等.

# C Linux 函数使用

1. void *dlopen(const char *path, int flags);

当前目录使用`./`开头. `flags`一般使用`RTLD_LAZY`, `RunTime LoaDer` 是前面所写的意思, 这个是说只在使用的时候载入这个plugin.

返回的是这个动态库的地址.

2. int dlclose(void *handle);
传入地址, 关闭动态库.

3. void *dlsym(void *restrict handle, const char *restrict symbol);
传入动态库的地址, 使用symbol调用函数, 返回对应的函数指针, 这里的symbol指的是函数的名字.

4. char *dlerror(void);
失败处理, 在上面的`dlopen`和`dlsym`实际上都需要做错误审查, 这里的错误审查不能使用`errno`, 必须使用`dlerror`这个函数.

他返回的是当前错误的原因, 是一个字符串.

一般来说, 我们会在我们获取一个函数之前, 我们先手动的使用这个函数清理掉之前的错误状态.

# Log

1. readdir 获取的信息存在了同一个地址, 所以使用动态数组存储这个值的时候, 必须拷贝出来. 否则会**双重释放**.

具体而言, 我们应该如下操作, 如下语境中的`d`指的是传入的`dirent`实例.

```C
struct dirent *copy = (struct dirent *)malloc(sizeof(struct dirent));
*copy = *d;
```

这里有意思的是, `*copy = *d` 这个操作, 这个操作获取了地址指向的值, 把缓冲区中的数据拷贝出来了. 这个我最开始没有想到.

2. **动态数组**

这个动态数组是一个有意思的数组, 这个数组是一个malloc动态分配的数组, 而他的每一个元素, 都是一个动态分配的元素.

我们会有一个问题, 释放`vector`和`vector[0]`是不是一样的?

因为我们认为`vector[0]`和`*(vector + 0)`一致.

这里我们就可以解释了, 答案是, 不一样. 我们释放了第一个元素, 没有释放这个列表本身.

证据就是, 我们释放`*(vector + 0)`指的就是数组首地址中存储的值, 而不是首地址本身, 而这个首地址存储的值, 就是第一个元素的地址.
```text
address value
0x0001 0x0002
0x0002 0x....
0x0003 0x....
0x0004 0x....
```
这样关于增删改查我们需要做的就是, 在每一次增加新元素的时候, 把这个**新的元素**拷贝.而之前的元素, 只需要使用`memcpy`**复制**一下就可以了.

# 优化Makefile

我希望优化我的makefile使用体验, 现在我的代码已经开始分文件架构了, 所以我必须重构我的代码.

在这种情况下, 我就不希望手动的添加所有的文件了, 我希望把过程拆开, 一步步的完成所有的任务.

我们来看一下我们需要完成什么.
1. 生成.o文件, 避免一次性构建整个项目

2. 生成.so文件, 避免手动生成.so插件

3. 优化清理, 运行等命令

## 涉及的知识点

1. `$<` 表示**依赖** `$@`表示**目标**, `%`是通配符, 与`*`一致, 但是为了保持与正则表达式分开, 所以我们使用`%`.
```makefile
$(BUILD)/%.o: src/%.c
	@mkdir -p $(BUILD)
	$(CC) $(CFLAGS) $(DEPFLAGS) -c $< -o $@
```
如上所示, 我们是说, 在变量`BULID`下新建`.o`文件, 他的名字是来自于依赖`src`下的`.c`文件.

这样我们就把`%.c`文件编译到了`.o`文件.

2. `wildcard`函数和`patsubst`函数
`wildcard`函数用于获取文件, 我们可以使用如下方式获取到我们需要的文件, 例如在`PLUGIN_SRC`中, 我们希望把所有的插件编译到`.so`文件, 所以自然需要使用到这个命令.

但是对于我们的目标文件, 这是未必的, 因为我们可以手动的写源代码的列表, 也就是采用类似于**白名单**的方式, 这样便于管理什么文件需要编译.

```makefile
PLUGIN_SRC := $(wildcard src/*.c)
```

`patsubst`函数用于模式替换(PATtern SUBSTitution), 然后进行替换, 简单的说, 就类似于vim中的s替换命令. 我们可以用这个方式来批量的生成我们需要的`.o`文件, 而不必我们手动的写出所有的文件

```makefile
OBJ := $(patsubst src/%.c, build/%.o, $(SRC))
```

语法是`$(patsubst 待替换文本, 替换后文本, 需要替换的文本)`.

所以以上的命令的意思就是说, 把`$(SRC)`中的`src/%.c`替换成`build/%.o`.

这里还有一个简写的模式

```makefile
OBJ := $(SRC:src/%.c=build/%.o)
```

语法就是`$(变量名=被替换模式=替换模式)`

3. `.d`文件

我们生成的`.o`文件会在他的源文件发生改变的时候, 重新编译, 但是对于他依赖的`include`头文件来说, 就不会触发自动补全.

这个是一个问题, 所以我们的可以使用`-MMD`命令为对应的文件生成对应的`.d`文件

`.d`文件本质是一个`makefile`文件, 里面是程序自动生成的对应的构建命令, 我们使用`-MP`来生成伪目标.

我们使用`-include $(OBJ:.o=.d)`在文件的最后引入了`.d`文件, 这里就是上面提到的`patsubst`的简写模式. 其实就是引入了一些构建的目标, 让我们的程序生成`.o`文件的时候, 不止依赖于`.c`文件, 也依赖于它的`.h`文件.

但是这里有一个问题, 如果我们不小心把`.h`文件删除的话, makefile会报错说找不到构建的目标, 这个报错是毫无意义的, 因为这不是问题, 他莫名其妙, 而且不是能帮助我们解决问题.

所以我们使用`-MP`命令生成对应的制作规则, 尽管他的内容是空. 但是他告诉我们的Make, 这个构建目标是存在的, 你不用管它. 所以当我们的`.h`文件不小心被删除之后, 报错的就是编译器, 而不是我们的构建系统
```makefile
build/utils.o: src/utils.c include/utils.h
include/utils.h:
```
给出一个具体的`.d`文件的例子, 我们就知道具体发生了什么了.

4. LDLIBS 参数

把编译期参数和链接器参数区分开, 之前是放在了一起, 但是`-ldl`是解释我们需要链接什么的.

```makefile
CFLAGS := -Wall -Wextra -pg -g -Iinclude
LDLIBS := -ldl
```
